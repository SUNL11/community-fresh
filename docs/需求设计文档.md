**版本**：v1.0

## 一、项目概述

### 1.1 项目背景

社区生鲜自提点、高校食堂窗口、夫妻店式生鲜小店是生鲜流通的末端节点。这些终端普遍面临三个结构性矛盾：

- **品控效率低**：到货清点、坏果排查完全依赖人工肉眼判断。单批次盘点耗时 5–10 分钟，且不同店员判断标准不统一，导致同一批货的品控结论因人而异。
- **损耗管控粗放**：损耗数据依赖手工纸笔登记，数据滞后至少一个盘点周期，且维度单一（通常只有"坏了多少"），缺少品类维度、时间维度、供应商维度的交叉分析。损耗规律无法被及时发现，造成可避免的食材浪费。
- **技术门槛高**：大型连锁商超使用的视觉分选设备（如 TOMRA、Compac）单台成本数十万元，且需要专业调试运维，小微终端根本无法承担。

### 1.2 项目目标

打造一款**零硬件门槛、轻量化、开箱即用**的 AI 工具：

- **输入**：仅需普通手机或电脑拍摄的图片
- **输出**：自动完成生鲜品类识别、数量统计、外观瑕疵检测
- **增值**：一键生成标准化损耗分析报表与管控优化建议
- **使命**：帮助小微生鲜终端以极低成本获得数字化品控能力，切实降低损耗

### 1.3 赛道定位

本方案属于**应用创意赛道**，核心创新点为**场景下沉的应用创新**，而非底层算法突破。方案紧扣 "乡村振兴 + 智慧城市" 双赛道方向：

- **乡村振兴**：赋能县域、乡镇生鲜零售末端的数字化升级
- **智慧城市**：以 AI 降低城市生鲜供应链末端的食材浪费

落地成本极低（仅需一台带摄像头的普通电脑）、可复制性强（全国数十万社区生鲜终端均为潜在用户），契合大赛"技术可行性 + 应用落地价值"的评审导向。

### 3.3 视觉检测模块（核心算法层）

#### 3.3.1 生鲜品类识别与计数

**模型选型**：主模型采用 YOLOv11n（nano 版本），官方 COCO 预训练权重，原生支持 apple、orange、banana 等类别。选择 nano 版本的理由：

- 模型体积仅 5.4MB，GPU 推理延迟约 15–30ms（NVIDIA CUDA）
- GPU 环境下可实现毫秒级实时检测，同时支持 CPU 兜底（约 250–650ms）

**技术流程图**：

```text
输入图片 → 预处理 (640×640 resize + normalize)
       → YOLOv11n 推理 (PyTorch CUDA / TensorRT)
       → 置信度过滤 (≥0.5)
       → NMS 去重 (IoU阈值 0.45)
       → 筛选 COCO 品类 (apple=47, orange=49, banana=52, 手动添加 tomato)
       → 按类别统计计数
       → 绘制检测框 (完好=绿色 框, 瑕疵=红色 框)
```

**性能优化策略**：

| 策略 | 预期收益 |
|---|---|
| 模型导出为 **TensorRT** 格式（`yolo export format=engine`） | GPU 推理速度提升 3–5x |
| 使用 **TensorRT EP / CUDA EP** 加速 | GPU 推理再提升 2–3x |
| 输入图片缓存最近一次推理的 tensor | 相同图片二次检测延迟降至 <100ms |
| 动态 batch size 支持（批量上传场景） | 多图吞吐量提升 2–3x |

#### 3.3.2 外观瑕疵检测（最简方案）

**核心逻辑**（基于颜色特征的零训练方案）：

```text
for each 检测到的目标框:
    1. 裁剪 ROI (扩展 5px 边界，避免边缘截断)
    2. 转换 HSV 色彩空间
    3. 根据品类选择色彩掩膜区间:
       苹果红色健康区: H(0-10, 160-180), S(50-255), V(50-255)
       橙子健康区:     H(5-25), S(40-255), V(50-255)
       香蕉健康区:     H(40-80), S(30-200), V(30-255)
       番茄健康区:     H(0-10, 160-180), S(40-255), V(40-255)
    4. 计算不符区域占比:
       defect_ratio = 非健康像素 / ROI 总像素
    5. 判定为瑕疵:
       if defect_ratio > 阈值(默认6%): 标记为瑕疵果
    6. 在瑕疵区域绘制红色热力图蒙版
```

**阈值自适应策略**：根据过去 30 次检测的健康果缺陷比均值动态调整阈值，减少光照变化造成的误判。

#### 3.3.3 可选进阶方案（微调训练）

若时间充裕（+2 天），可从以下路径提升瑕疵检测精度：

- **数据集**：Kaggle "Fresh and Rotten Fruits" 数据集 + 自行采集 50–100 张本地终端实拍图
- **策略**：在 YOLOv11n 基础上增加 `rotten` 类别，使用预训练权重做迁移学习
- **预期收益**：瑕疵识别准确率从 80% 提升至 90–95%
- **训练配置**：batch size=8, epochs=50, learning rate=0.001, 数据增强 (Mosaic + MixUp)

### 3.4 智能损耗报表模块（LLM Agent）

#### 3.4.1 技术架构

采用 **MCP (Model Context Protocol)** 风格的 Agent 架构实现报表生成：

```text
检测结果(JSON) → Prompt 模板引擎 → LLM API (豆包/通义千问/文心一言)
                                       ↓
                              结构化报表文本输出
                                       ↓
                              Gradio Textbox 展示
                                       ↓
                              一键复制 / 导出
```

#### 3.4.2 LLM Prompt 模板

```text
你是生鲜门店损耗分析专家"鲜小智"。请根据以下今日检测数据，生成一份简洁的日度损耗分析报表。

今日检测数据：
{
  "检测日期": "2026-07-21",
  "总数量": 34,
  "总瑕疵数": 5,
  "整体损耗率": "14.7%",
  "品类详情": [
    {"品类": "苹果", "数量": 12, "瑕疵数": 2, "损耗率": "16.7%"},
    {"品类": "橙子", "数量": 8, "瑕疵数": 1, "损耗率": "12.5%"},
    {"品类": "番茄", "数量": 10, "瑕疵数": 2, "损耗率": "20.0%"},
    {"品类": "香蕉", "数量": 4, "瑕疵数": 0, "损耗率": "0.0%"}
  ]
}

报表需包含以下 3 部分（每部分用 === 分隔）：

=== 今日损耗概览 ===
一句话概括整体情况，包含总数量、瑕疵总数、整体损耗率，与昨日对比趋势（如有历史数据）。

=== 重点损耗品类分析 ===
指出损耗率最高的品类，结合品类特性（如番茄皮薄易损）推测可能原因（运输挤压、存储温度、到货品质等），给出单品类视角的判断。

=== 管控优化建议 ===
输出 2-3 条贴合社区生鲜小店场景的实操建议，语言接地气、可直接执行。
建议类型可涵盖：采购建议、存储建议、陈列周转建议、到货验收标准优化等。

要求：语言简洁专业、适合门店经营者阅读，总字数 300 字以内。
```

#### 3.4.3 Agent 扩展能力

- **上下文记忆**：通过 SQLite 存储每日检测记录，Agent 在生成报表时可引用前一日数据做对比分析
- **工具调用**：当检测到某个品类损耗率连续 3 天上升时，Agent 自动触发"预警"标记，调整建议措辞为紧急
- **多模型备选**：配置化切换 API Provider，避免单点依赖

### 3.5 数据持久化与历史记录

采用 **SQLite** 零配置嵌入式数据库，无需安装额外服务：

**表结构设计**：

```sql
-- 每日检测主表
CREATE TABLE inspections (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    date TEXT NOT NULL,              -- '2026-07-21'
    timestamp DATETIME DEFAULT CURRENT_TIMESTAMP,
    total_count INTEGER,
    total_defect INTEGER,
    overall_loss_rate REAL,
    image_path TEXT,                 -- 原图备份路径
    annotated_image_path TEXT,       -- 标注图路径
    report_text TEXT                 -- 生成的报表文本
);

-- 品类明细表
CREATE TABLE inspection_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    inspection_id INTEGER NOT NULL,
    category TEXT NOT NULL,          -- 'apple', 'orange' 等
    count INTEGER,
    defect_count INTEGER,
    loss_rate REAL,
    FOREIGN KEY (inspection_id) REFERENCES inspections(id)
);

-- 单品检测框数据（用于后续分析）
CREATE TABLE detection_boxes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER NOT NULL,
    x1 REAL, y1 REAL, x2 REAL, y2 REAL,  -- 归一化坐标
    confidence REAL,
    is_defect BOOLEAN,
    FOREIGN KEY (item_id) REFERENCES inspection_items(id)
);
```

## 四、创新与前沿技术融合

### 4.1 MCP Agent 化报表生成

引入 **MCP（Model Context Protocol）风格**的 Agent 架构，将损耗报表生成从简单的 Prompt 调用升级为具备上下文感知的工具型 Agent：

- **Memory 模块**：存取近 7 天检测历史，使报表支持对比分析和趋势判断
- **Tool 注册**：注册 `query_history(category, days)`、`check_alert(category)` 等工具函数，Agent 根据数据分析需求自主选择调用
- **结果可解释性**：Agent 在输出报表时附带关键数据引用（"番茄损耗率 20.0%，高于近 7 天均值 12.5%"，来源：7 天历史查询），增强报表可信度

### 4.2 视觉语言模型（VLM）辅助增强

作为 YOLO + HSV 方案的补充，集成轻量级 VLM 做二次校验：

- 对于 HSV 判定为"边缘瑕疵"（缺陷比在阈值 ±2% 范围内）的样本，自动调用 VLM 做二次确认
- 可选 VLM：Qwen2-VL-2B / PaliGemma-3B，均可 GPU 加速运行，推理速度提升 5-10x
- 预期效果：降低光照变化和阴影带来的误判约 5–10 个百分点

### 4.3 边缘端 ONNX Runtime 部署

- 全部模型导出为 ONNX 格式，采用 **ONNX Runtime（CUDA EP）** 进行 GPU 推理
- 支持 **TensorRT EP（NVIDIA GPU 专属加速）**，推理延迟可降至 **5-10ms**
- 未来可直接移植到 Jetson Orin / 工业边缘 GPU 盒子

### 4.4 渐进式学习闭环（数据飞轮雏形）

- 每个检测结果提供"修正"入口：用户可手动纠正误识别的品类或瑕疵标记
- 修正数据自动落盘到 `corrections/` 目录，形成标注 backlog
- 当 backlog 累积到 200 张后，可一键触发增量微调训练，模型持续进化

## 七、可行性分析与风险评估

### 7.1 技术可行性

| 维度 | 评估 |
|---|---|
| 目标检测 | YOLOv11n 是成熟技术，COCO 原生覆盖目标品类，开箱即用 |
| 瑕疵检测 | HSV 颜色分析方法在实验室环境准确率可达 80%+，满足演示需求 |
| 报表生成 | 大模型 API 均已提供免费额度，Prompt 工程即可完成，无需自训练 |
| 整体架构 | Gradio + ONNX Runtime（CUDA EP）+ SQLite 均为成熟稳定的开源方案 |

### 7.2 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 堆叠遮挡导致漏计 | 中 | 提示用户分层摆放拍摄；提供"手动修正"入口 |
| 复杂光照导致瑕疵误判 | 中 | HSV 阈值自适应 + VLM 二次校验（可选） |
| 大模型 API 超时/限流 | 低 | 内置重试机制（3 次退避重试）；支持离线模板兜底 |
| CUDA 版本兼容性 | 低 | 锁定 CUDA 12.x + cuDNN 8.x + PyTorch 稳定版组合，避免版本不匹配 |
| VRAM 不足（4GB 下限） | 低 | YOLOv11n 仅占用约 1GB VRAM，常规 4GB 以上 GPU 均可流畅运行 |
